### 2.3 任务类型 / 业务领域 / 修改范围 / 任务难度

可选项见下文。如果有不在选项内的情况，可以联系 **@安琪** 增加新的选项。

### 2.4 任务是否完成

判断模型在**这一轮次**是否完成了用户的任务需求（只考虑结果，不考虑过程）。

- prompt 中没有提到的额外需求，**不能**作为判定未完成任务的依据
- 需结合第一轮整体需求，以及前面所有轮次迭代累加的全部整体需求，统一进行综合判定

### 2.5 产物及过程是否满意

判断模型执行任务的**过程及产物**是否让用户满意。

> ⚠️ **注意**：
> - 即使完成了任务，也有可能对产物和过程不满意，例如产物太丑了、过程规划混乱等
> - **过程是必须要看的哈，优先级最高**，看了过程之后，再看产物
> - 未完成任务但对产物一定是不满意的，产物不满意理由一定需要写

### 2.6 不满意原因

分点论述：

- **对产物不满意的原因**
- **对过程不满意的原因**

> 过程和产物都需要分析，不能产物不满意就不去看过程是否满意！！！

填写格式：

```text
产物不满意：xxx
过程不满意：xxx
```

### 第二步：与模型交互（每个多轮对话内不超过 5 轮）

- 出题请确保题型在下述范围内。Prompt 可以是自然语言描述，也可以是较为完整的 PRD

- 对于显然的**工程故障**（例如网络波动导致请求失败），不计入轮次
- 但是，对于**思考次数超限**需要人为"继续"的情况，应计入轮次
- 思考过程过长或者一直死循环可以直接打断，计入轮次，备注不满意，理由：死循环 / 思考时间过长

### 不满意理由填写要求：
不满意理由不能只写“无法运行、页面打不开、问题没修复、接口失败”等笼统结论，必须说明具体问题点。
合格的不满意理由应至少包含以下要素中的 两项及以上：
- 范围/对象
    问题发生在哪里：页面/路由、接口、功能模块、文件、命令、构建目标、运行环境、平台等。
- 现象/证据
    实际发生了什么：页面表现、报错信息、日志、编译错误、HTTP 状态码、操作步骤、复现结果等。
- 与需求的偏差
    相比第一轮主需求及有效迭代要求，缺了什么、错在哪里、期望是什么、实际是什么。
- 影响范围
    问题影响了哪些核心流程或功能：登录、下单、提交、跳转、数据展示、游戏流程、服务启动等。
- 复现条件
    在什么条件下出现：使用的账号、输入数据、浏览器/设备、运行命令、环境版本、特定操作路径等。
- 严重程度
    问题是阻塞主流程、部分功能异常、体验问题，还是边界场景问题。

#### 不合格写法
以下写法过于简单，不能作为合格的不满意理由：
产物不满意：无法启动
产物不满意：系统登录不了
产物不满意：网页无法打开
产物不满意：项目编译出错
产物不满意：服务不可用
产物不满意：问题没有修复
产物不满意：接口访问失败
产物不满意：长时间无输出
产物不满意：按 Z 依旧会闪退

问题在于：只写了结论，没有说明哪里出问题、有什么证据、与需求差在哪里。
#### 推荐模版

产物不满意：在【范围/对象】中，执行【操作/条件】后出现【现象/证据】。根据累计需求，期望【期望结果】，但实际【实际结果】，因此【影响/严重程度】。

#### 合格示例
产物不满意：在 /login 登录页中，输入正确账号密码并点击登录后，页面仍停留在当前页，没有跳转到首页。需求要求完成登录流程并展示用户信息，但实际登录后无跳转，导致核心登录流程不可用。
产物不满意：执行 npm run dev 启动前端项目时，控制台报xx模块缺失错误，导致本地xx页面无法访问。需求要求交付可运行项目，但当前无法启动验证功能，属于阻塞问题。
产物不满意：调用 POST /api/orders 提交订单接口时返回 500，前端点击“提交订单”后订单列表没有新增记录。需求要求用户能够完成下单流程，但当前提交环节失败，导致核心业务流程不可用。

## 八、常见问题解答

### 🛠️ 任务定义与轮次逻辑

**Q：数据提交是以"轮次"为单位吗？"一轮"的具体定义是什么？**

A：是的。每一个单轮对话（Single-turn）即为一条独立的数据。

- 一轮 = 一次交互（用户提问 + 模型回答）
- 即使是一个复杂的任务进行了多次对话，也需要拆分成多条数据提交

**Q：任务类型是根据当前轮次确定的，还是整个对话确定的？**

A：根据当前轮次确定。每一轮的标注都要基于该轮的实际内容。

- 示例：第一轮是"代码生成"，第二轮如果是修复第一轮的错误，则第二轮的任务类型应变更为"Bug 修复"

---

### 🔄 截断与"继续"处理

**Q：如果模型输出超长中断了，第一轮该如何评价？**

A：如果模型因为输出超长或不明原因的结束任务而导致过程及产物不完整，这一轮应判定为**"未完成任务"**且**"不满意"**。

**Q：对于用户输入了"继续"的轮次，提示词（Prompt）应该怎么写？**

A：请按照以下格式填写提示词：

```text
[用户实际提示词，如"继续"]（[上一轮提示词]）
```

示例 Prompt：

```text
[继续]（[这是一个基于 Vue 3 + Vite 的影院购票 web 项目，项目目前可以正常运行，并使用 mock 模拟后端影片、场次、用户订单全量数据。你要做的是聚焦前端影片详情模块和观影订单模块进行跨模块多文件的 Feature 迭代（即在已有功能基础上的平滑扩展），具体要求如下：在影片结算页面，会有 "同类型热映影片" 推荐卡片页面，在该卡片中添加一个选座购票按钮，点击会立即将影片场次加入当前待支付订单。]）
```

**Q：因"思考达到最大限度"而中断，和普通的"继续"逻辑一致吗？**

A：一致。很多情况下是因为模型思考超限才需要手动点"继续"。

> ⚠️ **注意**：如果中断是由于网络波动、请求失败等工程/网络原因导致的，**不应提交**该数据，建议重试。我们只评估由模型能力造成的表现。

---

### ⚖️ 评分与验收标准

**Q：数据验收是针对整个多轮对话会话，还是单轮数据？**

A：针对单轮进行验收，每一个单轮对话是一条数据。

**Q：如果模型前几轮翻车，但最后一轮修正了，该怎么评分？**

A：

1. **前几轮**：通常应该是"未完成"+"不满意"
2. **最后一轮**：结合专家个人体感评估
   - 如果是反复自纠、磕磕绊绊才完成，体感可能较差
   - 如果是突然"开智"、高效完成交付，即使前面有错，最后一轮也可以判定为**"满意"**

---

### 🎯 题目多样性与难度要求

**Q：业务领域覆盖有具体要求吗？**

A：必须覆盖**大前端与服务端**这类任务。其他类型不做硬性限制。

**Q：对任务的难度上限和下限有要求吗？**

A：

- **上限**：无量化要求，欢迎高难度挑战
- **下限**：有严格限制。**禁止**提交过于简单的题目（如简单的单文件代码理解）

**Q：同一个 repo 可以出多少题目？**

A：不限制，但是禁止雷同的 repo + 雷同的题目（包括第一期的数据）。

**Q：同一个对话窗口里，第 2、3、4、5 轮提问，是否只能围绕第一轮需求做补充 bug 修复、细节优化？不能中途更换需求、新增无关新功能？**

A：是的！

**Q：是否可以上传附件？**

A：多模态附件和长的纯文本附件可以。如果是比较短的纯文本附件，直接复制粘贴到对话框作为提示词直接发送。

- 如果超出 prompt 长度限制就用文件，或者放在项目内用路径也可以
- 如果没有超过 prompt 长度最好是粘贴进来，可以考察下模型的长文能力
- 如果是上传附件这种，必须将附件上传到截图列，不会因此而提高 AHT，请衡量性价比

**Q：什么样的题目是"过于简单的题目"？**

A：同时满足下述两种及以上特征的题目，是过于简单的题目，拒收：

> 暂时无法在飞书文档外展示此内容

**Q：第一轮开发完成后，程序无 bug，但部分显性功能未实现，该如何定义产物状态？**

A：应标记为任务未完成、产物不满意。

**Q：第二轮针对第一轮缺失的显性功能进行补充完善，属于什么开发类型？**

A：属于迭代开发。

**Q：当前轮次任务是否完成，依据什么来判定？**

A：需结合第一轮整体需求，以及前面所有轮次迭代累加的全部整体需求，统一进行综合判定。

**Q：隐形需求未完成，能否判定为本轮任务未完成？**

A：不能，隐形需求未完成不做为任务未完成的判定依据。

## 九、过程分析提示词

```text
你是过程质检员。请基于输入信息判断"本轮执行过程是否满意"。

【输入】
- User Prompt: 本轮用户提示词
- 轮次: 本轮轮次（第几轮）
- 日志轨迹: 本轮完整执行日志（含思考、工具调用、报错、重试、最终动作等）

【判定目标】
仅判断"过程是否满意"，不直接判断最终产物质量。

【过程满意判定维度】
1. 需求理解与对齐
   - 是否正确理解 user_prompt 意图
   - 是否有明显跑题、误解、无关展开

2. 过程规划与推进效率
   - 是否有清晰推进步骤
   - 是否出现无效循环、重复尝试、明显拖沓
   - 轮内行动是否与目标相关

3. 工具使用与故障处理
   - 工具调用是否必要且顺序合理
   - 失败后是否有有效回退/替代方案
   - 对环境故障是否做了合理说明（不可把纯环境故障直接算模型过程差）

4. 沟通体验
   - 是否及时反馈关键进展
   - 是否在关键不确定点进行必要澄清
   - 语气是否自然、不过度模板化

【不满意判定建议】
出现以下任一情况可判"不满意"：
- 明显误解需求且未自我纠正
- 多次无效重复操作，缺少收敛
- 工具使用混乱导致过程冗长
- 关键失败无解释、无替代路径
- 沟通缺失导致用户无法判断进展

【输出要求】
只输出 JSON，且仅两个字段：
{
  "过程是否满意": "满意/不满意",
  "不满意原因": ""
}

规则：
- 若为"满意"，不满意原因 必须为 ""。
- 若为"不满意"，不满意原因 必须为 string，并在同一字符串中按序号列出："1、... 2、... 3、..."
- 原因只写"过程问题"，不要写产物质量问题。
