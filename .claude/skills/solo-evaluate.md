# solo-evaluate

分析 Trae Solo Coder 的 trace 日志和项目 git diff，自动评估当前轮次并生成结构化的交付字段。

## 使用方式

```
/solo-evaluate <项目名> [轮次号]
```

例如: `/solo-evaluate tsp2-standard-system-tree 1`

## 执行步骤

### 1. 收集信息

- 读取 `projects/trae-solo/<项目名>/` 下的项目代码
- 读取 `docs/result/` 下对应的 trace 日志文件（如果存在）
- 如果用户提供了 trace 日志内容，直接使用
- 检查 git 分支 `<项目名>` 上的 diff（与 main 分支对比）

### 2. 分析 trace 日志

从 trace 日志中提取：
- 模型执行了哪些工具调用（view_files, edit_file, run_command 等）
- 是否有失败的操作（status: failed）
- 是否有反复重试、死循环
- 是否有明确的任务完成声明
- 执行过程是否高效有序

### 3. 分析代码产物

从 git diff 和项目代码中判断：
- 修改了哪些文件，涉及几个模块
- 代码是否能编译/运行（检查明显语法错误）
- 功能是否完整实现（对照原始 prompt 需求）

### 4. 输出结构化评估

输出以下字段的建议值：

```
## 评估结果

| 字段 | 建议值 | 判定依据 |
|------|--------|----------|
| 任务类型 | [Bug 修复/0-1 代码生成/Feature 迭代/代码理解/代码重构/工程化/代码测试] | ... |
| 业务领域 | [纯后端 API 服务/Web 前端/全栈 Web 应用/...] | ... |
| 修改范围 | [无需修改/单文件/模块内多文件/跨模块多文件/跨系统多模块] | ... |
| 任务难度 | [一般/较难/困难] | ... |
| 任务是否完成 | [完成了任务/未完成任务] | ... |
| 产物及过程是否满意 | [满意/不满意] | ... |

### 过程分析
- 需求理解：...
- 推进效率：...
- 工具使用：...
- 沟通体验：...

### 产物分析
- 功能完整性：...
- 代码质量：...
- 可运行性：...
```

## 判定规则

### 任务类型判定
- 第一轮通常是 "0-1 代码生成" 或 "Feature 迭代"
- 后续轮如果是修复前轮错误 → "Bug 修复"
- 后续轮如果是补充功能 → "Feature 迭代"

### 修改范围判定
- 统计 diff 涉及的文件数和目录结构
- 同一目录下多文件 → "模块内多文件"
- 跨 frontend/backend → "跨系统多模块"
- 跨不同功能模块目录 → "跨模块多文件"

### 完成度判定
- 对照原始 prompt 中的每个显性需求点
- 隐性需求（prompt 未提及的）不作为未完成依据
- 需结合所有前序轮次的累加需求

### 满意度判定
- 过程优先：先看过程是否高效有序
- 再看产物：功能是否完整、能否运行
- 即使完成了任务，过程混乱也可判不满意
