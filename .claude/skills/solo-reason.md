# solo-reason

基于 trace 日志和运行结果，生成符合甲方质量要求的不满意原因。

## 使用方式

```
/solo-reason <项目名> [轮次号]
```

或直接粘贴 trace 日志后调用。

## 甲方要求

不满意理由必须包含以下要素中的 **两项及以上**：

1. **范围/对象** — 问题发生在哪里：页面/路由、接口、功能模块、文件、命令、构建目标、运行环境、平台等
2. **现象/证据** — 实际发生了什么：页面表现、报错信息、日志、编译错误、HTTP 状态码、操作步骤、复现结果等
3. **与需求的偏差** — 相比第一轮主需求及有效迭代要求，缺了什么、错在哪里、期望是什么、实际是什么
4. **影响范围** — 问题影响了哪些核心流程或功能
5. **复现条件** — 在什么条件下出现
6. **严重程度** — 阻塞主流程、部分功能异常、体验问题、还是边界场景问题

## 关键原则：像人说话

生成的不满意原因必须像一个真实的开发者在写反馈，不能有 AI 味道：

- 不要用 markdown 格式（不要加粗、列表、标题）
- 不要用"首先""其次""综上所述"这类连接词
- 不要用过于工整的排比句式
- 可以有口语化表达，比如"试了几次都没成功""这块逻辑明显有问题"
- 句子长短不一，不要每句都差不多长
- 可以带点主观判断，比如"感觉是没理解需求""这个实现方式有点绕"
- 不要每段都完美覆盖所有要素，自然地融入 2-3 个要素即可

## 执行步骤

### 1. 分析 trace 日志

- 找出所有 `status: failed` 的工具调用
- 找出反复重试的操作（同一文件编辑多次失败）
- 找出死循环或无效操作
- 找出 run_command 的报错输出

### 2. 分析产物问题

- 对照原始 prompt 的需求清单
- 检查代码中的明显错误（导入缺失、语法错误、接口不匹配）
- 检查是否有未实现的功能点

### 3. 生成不满意原因

分别输出产物和过程的不满意原因，用纯文本，像人在聊天框里打字的感觉。

## 禁止的写法

以下会被驳回（太笼统）：
- "无法启动"
- "系统登录不了"
- "网页无法打开"
- "项目编译出错"
- "问题没有修复"

以下会被识别为 AI 生成（太工整）：
- 每句都用"在...中，执行...后，出现..."的固定句式
- 用"综上""总结来说""具体表现为"等书面连接词
- 产物和过程原因长度完全一样、结构完全对称

## 合格示例

示例 1：

产物不满意：前端新建的标准体系管理页面写好了但没配路由，从菜单根本点不进去。需求里明确说要"新增标准体系管理页面"，结果页面文件倒是创建了，就是没法访问，等于白做。后端接口倒是都加上了，但前端这块整个功能入口都不通，主流程走不下去。

过程不满意：中间编辑 ServiceImpl 那个文件的时候失败了一次，search_replace 没匹配上，虽然后面重新读文件恢复了，但整个过程做完之后没有跑一下编译或者启动验证，直接就说完成了。连最基本的 npm run dev 都没执行过，不确定代码到底能不能跑。

示例 2：

产物不满意：调 /api/standardSystem/tree 这个接口，返回的数据是扁平的列表，没有按 parentId 组装成树形结构。前端 el-tree 组件拿到这个数据渲染不出层级关系，只能看到一堆平铺的节点。需求要的是完整的多级树，这个差距比较大，核心的树形浏览功能用不了。

过程不满意：实现 moveNode 的时候对同一个文件连续编辑了 4 次都失败，一直在用 search_replace 但匹配不上，也没想着换个方式（比如直接重写整段），最后这个功能就没实现。感觉在这块浪费了不少时间，大概有三分之一的操作都是无效重试。
