# solo-next

基于当前轮次的 trace 日志和评估结果，生成下一轮的 prompt，引导 Solo Coder 修复问题或补全功能。

## 使用方式

```
/solo-next <项目名> [轮次号]
```

例如: `/solo-next tsp2-standard-system-tree 1`

## 关键原则：像真人在对话框里打字

生成的 prompt 必须像一个真实用户在 IDE 对话框里输入的内容：

- 不要用 markdown 格式（不要标题、列表符号、加粗）
- 不要用"请""麻烦""帮我"开头的每一句话（偶尔用一次可以）
- 可以有口语化表达，语气随意一点
- 句子之间可以用逗号或句号自然连接，不要编号列表
- 不要写得像需求文档，要像开发者之间的对话
- 长度适中，不要太短（一句话）也不要太长（一整页）
- 可以带点情绪，比如"这块还是有问题""上次那个没修好"

## 设计原则

1. 精准定位问题 - 明确说哪里出了问题，不要泛泛而谈
2. 给修复方向 - 提示可能的解决路径，但不要写出完整代码
3. 保持需求连贯 - 围绕第一轮的原始需求
4. 避免过度引导 - 不要把答案直接写在 prompt 里
5. 控制范围 - 每轮聚焦 1-2 个核心问题

## 执行步骤

### 1. 分析当前轮失败点

从 trace 日志和评估中提取：
- 哪些功能未实现或实现错误
- 哪些文件有编译/运行错误
- 哪些接口不通或返回异常
- 前端页面哪些交互不工作

### 2. 确定下轮优先级

按严重程度排序：
1. 阻塞性问题（编译失败、服务无法启动）
2. 核心功能缺失（主流程不通）
3. 功能不完整（部分需求未实现）
4. 体验问题（UI 不合理、交互不流畅）

### 3. 生成 prompt

输出纯文本的 prompt，然后附上策略说明（策略说明是给自己看的，不发给 Trae）。

## 禁止的写法

以下会被甲方识别为模板化/AI生成：
- 用编号列表写需求（1. 2. 3.）
- 每句都用"请"开头
- 用"具体来说""需要注意的是"等连接词
- 结尾用"谢谢""辛苦了"
- 格式过于工整，像需求文档

## 合格示例

示例 1（修复启动问题）：

上次写的代码跑不起来，npm run dev 之后控制台报了个模块找不到的错，看起来是 standard-system/index.vue 这个页面没有在路由里注册。你把路由加一下，然后在左侧导航菜单里也加个入口，叫"标准体系管理"就行。加完之后跑一下确认页面能正常打开。

示例 2（修复接口问题）：

tree 接口返回的数据不对，现在返回的是扁平列表，没有按 parentId 嵌套成树形结构。前端 el-tree 需要的是 children 嵌套格式的数据，你看下 getTree 方法里的逻辑，应该是要递归组装一下。顺便确认下 move 接口能不能正常改变节点的 parentId 和排序。

示例 3（补全功能）：

右侧的统计面板还没做完，现在选中一个体系节点之后右边是空的。需求里说要展示标准总数、级别分布饼图、年份分布柱状图、还有健康度雷达图。你把这几个图表加上去，数据从 /api/standardSystem/{id}/stats 和 /api/standardSystem/{id}/health 这两个接口拿。ECharts 项目里已经装了，直接用就行。

## 注意事项

- 如果已经是第 4 轮，prompt 应该聚焦最关键的 1 个问题
- 如果已经是第 5 轮，不应再生成 prompt（已达上限）
- 不要在 prompt 中写出完整的代码实现
- 每次生成的 prompt 措辞要有变化，不能每次都一个套路
