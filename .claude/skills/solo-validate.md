# solo-validate

提交前合规校验，检查当前记录是否满足甲方所有验收要求，避免被驳回。

## 使用方式

```
/solo-validate <项目名>
```

或在填写完表格字段后调用，自动检查所有轮次记录。

## 校验规则清单

### 红线规则（违反即作废）

| # | 规则 | 检查方式 |
|---|------|----------|
| 1 | 第一轮不能是单文件修改 | 检查第一轮的 git diff 涉及文件数 |
| 2 | 不能是过于简单的题目 | 检查题目难度和修改范围 |
| 3 | 不能刻意凑满 5 轮 | 检查后续轮次是否有实质性新需求 |
| 4 | 已检出问题必须填报异常原因 | 检查不满意时是否有原因 |
| 5 | 禁止单文件代码理解类题目 | 检查任务类型和修改范围组合 |
| 6 | 仅一轮数据不能超过总量 8% | 统计单轮任务占比 |

### 字段完整性检查

| 字段 | 校验规则 |
|------|----------|
| Session ID | 非空 |
| User Prompt | 非空，且不能与其他题目高度相似 |
| 任务类型 | 必须在选项范围内 |
| 业务领域 | 必须在选项范围内 |
| 修改范围 | 必须在选项范围内，且与实际 diff 一致 |
| 任务难度 | 必须在选项范围内 |
| 任务是否完成 | 非空 |
| 产物及过程是否满意 | 非空 |
| 不满意原因 | 不满意时必填，且必须符合质量要求 |
| GitHub 地址 | 非空，格式正确 |
| 日志轨迹 | 非空 |

### 不满意原因质量检查

不满意原因必须包含以下要素中的 **至少两项**：
1. 范围/对象
2. 现象/证据
3. 与需求的偏差
4. 影响范围
5. 复现条件
6. 严重程度

**自动检测不合格写法**：
- 少于 30 字的理由
- 只有结论没有证据的理由
- 包含以下关键词但无具体描述："无法启动"、"登录不了"、"无法打开"、"编译出错"、"不可用"、"没有修复"

### 轮次逻辑检查

- 多轮对话中，后续轮次必须围绕第一轮需求
- 任务类型应与轮次逻辑一致（第一轮后的修复应标为 Bug 修复）
- 未完成任务时，产物必须标为不满意

### 修改范围一致性检查

- 统计 git diff 实际涉及的文件和目录
- 与填写的修改范围进行对比
- 如果 diff 跨前后端但填了"模块内多文件"，标记为不一致

## 输出格式

```
## 合规校验结果

### ✅ 通过项
- [通过的检查项列表]

### ❌ 不通过项
- [问题描述 + 修复建议]

### ⚠️ 警告项
- [可能有问题但不确定的项]

### 统计信息
- 总题目数：N
- 单轮题目数：M（占比 X%，要求 < 8%）
- 业务领域覆盖：[已覆盖的领域列表]
- 缺失覆盖：大前端与服务端类（必须覆盖）
```
